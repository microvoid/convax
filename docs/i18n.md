# Convax internationalization

[English](i18n.md) | [中文](i18n.zh.md)

## Summary

Convax uses the existing DSH locale service for language selection, persistence, dictionary lookup and live UI updates. Convax owns its UI dictionaries, package metadata and checks; third-party plugins own their namespaces. The DSH runtime remains unchanged.

## Shared language preference

The DSH Language setting selects `en`, `zh`, `ja`, `es`, `fr`, `de`, `ru` or `pt`; language-pack plugins can register additional languages. An explicit preference takes priority over the provisional browser or Desktop system language. DSH persists `locale.preference` through its existing settings service. When the Convax launcher supplies `.convax` as its application home, that same preference belongs to that home; Convax does not maintain another language setting.

The locale runtime resolves a key through the active language’s fallback chain in the requested namespace, then the `common` namespace, and finally the key itself. English terminates language fallback chains. Missing translations must be caught by checks rather than treated as support for the selected language. See the [DSH locale reference](../libs/dsh/packages/client/locale/README.md).

<a id="resources"></a>
## Resource ownership

The runtime namespace is `convax`. [`src/client/locales/en.ts`](../packages/plugin-renderer/src/client/locales/en.ts) defines its key type; each other language supplies a complete dictionary with the same interpolation parameters. [`locales.ts`](../packages/plugin-renderer/src/client/locales.ts) exports `dictionaries`, `SUPPORTED_LOCALES` and `ConvaxLocale`. The renderer registers these dictionaries through an effect-owned `ctx.locale.register` call.

Package `locale/<language>.json` files contain `meta.title` and `meta.description` for Plugin Manager. They are package metadata, not another copy of the UI dictionary. DSH resolves that metadata with `ctx.locale.resolveText`; it does not automatically register arbitrary JSON fields as a runtime namespace.

Third-party features use a provider-qualified namespace such as `example.counter`. Declare its keys in `LocaleNamespaceMap`, register its dictionaries with `ctx.effect(() => ctx.locale.register(namespace, dictionaries))`, and preserve every named placeholder such as `{name}`. Contributions do not add their keys to Convax’s central dictionary.

<a id="plugins"></a>
## Plugin rendering

Slot and Factory declarations carry a `locale` namespace. Their injected `t` changes with the locale revision so mounted and memoized UI receives fresh copy. `ctx.locale.bind(namespace)` returns a stable function that reads the current language when called; call it while rendering instead of saving its translated result during registration. Components outside the Slot/Factory path must subscribe to `ctx.locale.getSnapshot` and `ctx.locale.subscribe` before deriving display text.

A node renderer receives Convax’s translation seat for common card behavior. Wrap business content in its own locale-aware Factory when it needs its own translation seat, stores or child slots. A small component can instead call its bound namespace function inside the node render callback, as the shipped examples do:

```js
const t = ctx.locale.bind('example.counter')
ctx.inject(['convaxRenderer'], (scope) => {
  scope.convaxRenderer.registerNodeRenderer('example.counter', {
    dataVersion: 1,
    component: props => h(Counter, { ...props, title: t('title') }),
  })
})
```

The snippet assumes the plugin has registered its dictionaries and provides `h` and `Counter`. See the runnable [counter example](../packages/plugin-renderer/examples/counter/client.js) and [canvas-note template](../packages/plugin-host/templates/canvas-note/client.js). Both retain their own namespace and translate labels during rendering.

A public third-party toolbar-action API is not implemented. Its design must carry the plugin locale namespace and `labelKey`; the renderer resolves labels, tooltips and execution feedback with the current translation seat. A future registration must not freeze `label: t("action")` into a string at plugin activation. This is an API design requirement, not an available registration method.

## Failures and saved titles

Host diagnostics remain available for debugging, while user-facing explanations are localized in the Client. Command failures keep stable `code` values such as `conflict`, `not-found` and `invalid-command`; node problems use their stable `kind`; Chat problems use `issueCode` (`thread-create`, `deletion`, `delivery` or `chat-unavailable`). Raw `message` and `issue` text belongs in the expandable technical-details surface. Clients must not infer a failure category by matching English text.

A canvas can retain a system naming recipe in `titleFormat`: `default` displays the localized untitled name; `literal` retains its `value`; `copy` recursively renders its `source` and applies the localized copy-name template. The existing `title` remains the literal fallback. Explicit renaming removes the recipe. A Chat node with `data.defaultTitle: true` displays the localized untitled Chat label instead of treating its saved fallback as user-authored text.

Old records without these markers remain literal, including titles that happen to equal a translated default. Migration never guesses ownership from a title string. Switching language does not rewrite user titles, file paths, note bodies or Session messages. Convax owns the schema upgrade and its recovery copy.

## Formatting and verification

Pass the active DSH locale to `Intl.DateTimeFormat` and `Intl.NumberFormat` for user-visible dates and numbers. Explicit machine formats such as media timecodes and protocol values retain their defined representation. Do not let the browser’s unrelated default language decide formatting after the user chooses a language in DSH.

Run these checks from the outer Convax repository:

```sh
pnpm run check:i18n
pnpm run test:i18n:e2e
```

The static check covers Convax-owned dictionaries, package metadata, examples and templates: missing languages or keys, changed interpolation parameters, invisible characters and embedded UI copy. Browser E2E uses the production Web composition and real Language setting to exercise mounted cards, persisted preferences and preserved user content. Run the relevant E2E after each implementation step; built-browser runs require current artifacts. No API key is required for this language-switching path.
